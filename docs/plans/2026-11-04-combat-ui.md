## Approach

**One rule:** the UI never changes combat state. It builds `Command`s, calls
`CombatSession.submit`, shows `command_rejected` reasons, and redraws from state and facts. Facts
reach the screen through `FactPlayback`, which paces them; the board animates each fact as it
plays, and anything that must wait for the player (none in M1) uses a `PresentationRequest`.

**Shape:** the battle screen (`gameplay.tscn`, kept as the router's GAMEPLAY scene) holds a
`BattleView` (the map scene instanced for terrain, unit tokens, overlays for move, attack, danger
and darkness, the cursor, the camera), a `PanelHost` (action menu, target picker, forecast) and the
HUD. A `BattleController` turns input into commands, one state per step of question 6's flow.
View-models (plain data built from the session) sit between state and widgets, so tests check them
without rendering.

**Nothing here is permanent, and everything is editable** (user, November 4, 2026). This UI is
scaffolding for M1's playtest; layout, look and flow will be redone. So every step builds for easy
hand editing in the Godot editor:

- **Every component is its own `.tscn`:** the board, each overlay, the unit token, the cursor, the
  action menu, the target picker, the forecast panel, each HUD widget, the banners. A screen
  composes them by instancing, never by building nodes in code. Code creates nodes only for
  repeated instances of a saved scene (a token per unit, a menu row per action).
- **Layout, sizes, colours and fonts live in the scenes and one shared theme `.tres`**, not in
  scripts. Values a designer would tweak (colours per side, overlay alpha, playback timings) are
  documented `@export`s on the scene's root, so they show in the Inspector.
- **Scripts stay small and readable:** one script per scene, named after it, reaching its own
  children through `%UniqueName` nodes, never long `get_node` paths into other scenes. Widgets
  take a view-model and draw it; they hold no rules.
- **Each report lists the scenes it added** and what to edit in each, so they can be found later.

**Rejected:** porting `combat_ui.gd`'s factory of `create_*` methods (it connects panels straight to
the controller and lets them mutate state); polling state every frame instead of redrawing on
`batch_resolved` and playback.

## Save Impact

Not saved in M1: the screen holds only presentation state (selection, cursor, overlays, the
danger-zone toggle), rebuilt from the session at any time. Resuming a battle is P02 CC10. UI6's
opening-swap setting is per player and saved with the player's settings (`PlayerSaveSection`; key
and version stated in UI6's estimate).

## Rollback

Each step is its own merge. Reverting UI1 restores the placeholder screen; the combat code is
untouched by every step except UI3's text pass, which reverts with its snapshots.
